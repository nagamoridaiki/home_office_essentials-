# EC MVP 設計書

新品・中古の EC 販売と「買取 → 検品 → 中古として再出品」の循環に関する設計書を置いている。

## 1. このディレクトリの読み方

- **全部読まないこと。** 4 本の合計は約 31,000 トークンあり、読むだけでコンテキストを使い切る。
- まずこの README の「3. 問いから引く」で場所を特定し、**必要な章だけ**開く。
- 章だけ開くときは、見出しの行番号を出してから、その範囲だけ読む。行番号は編集で変わるので、毎回この方法で引く。
  - 見出しを出す: `grep -n '^##' 03-logical-data-model.md`
  - 出た行番号から次の見出しの手前までを読む（Read の `offset` / `limit`）
- 章の中でも、表の特定の行だけ必要なら grep で引く（例: `grep 'inspected' 02-state-transitions.md`）。
  - 取った行の列の意味が分からないときは、その表の見出し行を引く（例: `grep -n '^| メソッド' 04-api-list.md`）。
- `02` と `03` の 3 章（Mermaid の図）は人が全体像を見るためのもの。実装では表を読み、図は開かない（遷移は `02` の 4 章、関連は `03` の 2 章「主な関連」列にある）。
- `diagrams/*.svg` は開かない。人が見るための画像で、中身は座標だらけの XML（7 枚で約 56KB）。同じ情報は `02` の 4 章と `03` の 4 章の表にある。

## 4. 決まっていること

結論だけ。理由は各設計書にある。

- 認証は MVP では自前実装。将来 Cognito などの OIDC に切り替える前提で境界を切っている
- 決済手段はカードのみ（Stripe）
- 注文確定は Stripe の Webhook を正とする。入金前の注文レコードは作らない
- 在庫ソフトロックは専用テーブルを作らず `inventories` の 2 列で持つ（15 分）
- 売却済の在庫は在庫に戻らない。返品は新しい在庫行を作る
- 顧客向け URL は `public_id uuid`。人が読む番号は `ORD-2026-000042`（年でリセットしない）
- カートはサーバに持たない（ブラウザの `localStorage` に販売枠 ID のみ）
- API パスにプレフィックスを付けない。顧客自身のリソースは `/me/` 配下
- ステータスは `text` ＋ `CHECK`。Postgres の enum 型は使わない

## 5. 不変条件

壊してはいけない 3 つ。**正は `03` の 6 章**で、以下はその要約。

1. **1 点ものが二重に売れない** — 在庫の lock 2 列、`FOR UPDATE SKIP LOCKED`、`selling_order_items.inventory_id` の UNIQUE、Webhook のイベント ID の UNIQUE
2. **在庫ステータスが不正に遷移しない** — ステータス列の `CHECK`、許可遷移だけの実装、横断 `CHECK`
3. **他人の個人データ・税務データに URL を書き換えても到達できない** — 顧客と管理者のテーブル分離、`public_id`、`/me/` 配下への集約、ミドルウェアでの認可
